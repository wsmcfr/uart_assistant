# 真实设备端到端验证

本文用于第三阶段通信可靠性验证。目标是让串口 Raw、OTA、X/YMODEM 和 HID 的实机结果可复现、可记录、可定位，而不是只凭一次手工观察判断。

## 验证前准备

| 项目 | 要求 |
|------|------|
| 程序版本 | 使用 `D:\comassistant\build_release\ComAssistant.exe`，记录 Git commit 和构建时间 |
| 日志模板 | 使用 [真实设备验证日志模板](real-device-validation-log-template.md) 记录每次验证 |
| 串口设备 | 至少准备一个可回显或可接收文件的 MCU/Bootloader，记录芯片型号、固件版本和串口参数 |
| OTA 设备 | 准备能解析自定义 OTA 文件头、数据包、结束包和可选 ACK 的 Bootloader |
| X/YMODEM 设备 | 准备能返回 `C`、`G`、`NAK`、`ACK`、`CAN` 的标准 Bootloader 或终端工具；YMODEM-G 需优先使用硬件流控或低误码链路 |
| HID 设备 | 准备已知 Input、Output、Feature Report 长度和 Report ID 的 HID 设备 |

## 通用记录字段

每条实机验证至少记录这些字段：

| 字段 | 内容 |
|------|------|
| 环境 | Windows 版本、Qt 构建目录、ComAssistant commit |
| 设备 | 设备型号、固件版本、VID/PID/接口号或 COM 口 |
| 参数 | 波特率、数据位、停止位、校验位、Report 长度、块大小、包间隔、ACK token |
| 文件 | 文件名、大小、CRC32 或 SHA256 |
| 操作 | 具体点击路径、暂停/继续/取消/重试操作 |
| 结果 | 成功、失败、失败阶段、错误文本、截图或日志片段 |
| 定位 | 若失败，记录是队列拒绝、底层写失败、设备 ACK 超时、校验失败、HID 打开失败还是关闭释放异常 |

## 串口 Raw 分块发送

| 步骤 | 操作 | 期望结果 |
|------|------|----------|
| 1 | 选择串口并打开连接 | 状态栏显示已连接，发送队列为空 |
| 2 | 打开“发送文件”，选择“裸流分块” | 文件信息显示文件名、大小、CRC32、分块数 |
| 3 | 使用 256 B、1024 B、4096 B 三组块大小分别发送 | 进度按块推进，最终进入“传输完成” |
| 4 | 发送中点击“暂停”，等待 3 秒后点击“继续” | 状态显示“已暂停”后恢复“传输中”，数据不跳块 |
| 5 | 发送中点击“取消” | 状态经过“正在取消”并最终停止，设备端不再收到后续块 |
| 6 | 断开连接后尝试发送 | 传输失败并显示本地发送失败或连接未打开原因 |

失败定位重点：

- 如果进度提前到 100%，检查是否绕过了本地发送队列确认。
- 如果设备端丢块，降低块大小或增加包间隔，并记录设备端串口缓冲区大小。
- 如果取消后仍继续发送，检查发送队列是否仍有旧文件块未清空。

## 自定义 OTA 流式发送

| 场景 | 操作 | 期望结果 |
|------|------|----------|
| 无 ACK OTA | 关闭“等待 ACK”，发送小文件和大文件各一次 | Header、Data、DONE 按顺序发送，进度只统计数据 payload |
| ACK OTA | 开启“等待 ACK”，设置 `ACK` token、超时和重试次数 | 每包本地发送成功后等待设备 ACK，ACK 后发送下一包 |
| ACK 超时 | 设备端故意不回 ACK | 达到最大重试次数后进入失败，错误文本包含等待 ACK 超时 |
| 暂停继续 | ACK 模式下在等待 ACK 和等待下一块两个阶段分别暂停 | 暂停期间不继续读文件；继续后仍处理同一包或下一块 |
| 取消 | 发送中取消 | 状态经过“正在取消”，定时器停止，文件句柄释放 |

失败定位重点：

- Header 解析失败时，对照 magic、文件大小、CRC32、块大小和文件名长度字段。
- 数据包校验失败时，对照块序号、payload 长度和 CRC16-XMODEM。
- DONE 后设备端 CRC32 不一致时，确认设备端是否按完整文件内容计算，而不是按 OTA 包内容计算。

## XMODEM/YMODEM

| 场景 | 操作 | 期望结果 |
|------|------|----------|
| XMODEM-CRC | 设备端进入接收并发送 `C`，应用选择 XMODEM-CRC | 开始握手后发送 128 字节包，ACK 后推进 |
| XMODEM-1K | 设备端支持 1K 包时选择 XMODEM-1K | 每包 1024 字节，最后不足部分使用 `0x1A` 填充 |
| YMODEM | 选择 YMODEM 并发送文件 | 先发送文件头，再发送数据包，最后发送结束头 |
| YMODEM-G | 选择 YMODEM-G 并发送文件 | 接收端用 `G` 请求头包和数据流；应用不等待逐数据包 ACK，逐包发送数据并在 EOT 后等待 ACK+G |
| YMODEM-G 接收 | 应用选择 YMODEM-G 接收，设备端发送文件 | 应用先发送 `G`，成功数据包不逐包 ACK，EOT 后发送 `ACK+G` 请求下一文件头 |
| YMODEM-G 错误 | 设备端故意发送坏 CRC 或错包号 | 应用发送多字节 `CAN`，释放目标文件并显示失败原因 |
| 接收方取消 | 设备端发送 `CAN` | 应用停止传输并显示接收方取消 |
| 校验失败 | 设备端故意返回 `NAK` | 应用重发当前包，超过最大重试后失败 |

失败定位重点：

- 一直等待开始时，抓取设备端是否发送 `C`、`G` 或 `NAK`。
- 重试次数增长时，记录包号、校验方式和设备端返回字节。
- 传输完成但文件不一致时，确认 Bootloader 是否剥离 `0x1A` 填充。
- YMODEM-G 不支持 NAK 重传；如果链路会频繁出错，应改用普通 YMODEM 或降低速率。

## HID Report 验证

| 场景 | 操作 | 期望结果 |
|------|------|----------|
| 设备枚举 | 刷新 HID 设备列表 | 显示名称、VID、PID、接口号，未启用 hidapi 时给出明确提示 |
| 打开关闭 | 打开 HID 后连续关闭、重新打开 5 次 | 不崩溃、不残留线程，状态正确切换 |
| Output Report | 设置 Output 长度、Report ID 和 payload 后发送 | 设备收到完整 Output Report，历史记录方向和 HEX |
| Input Report | 设备主动上报 Input Report | 应用历史显示归一化后的 payload，可按配置移除输入 Report ID |
| Feature Set/Get | 连续点击 Set Feature 和 Get Feature | Feature 操作串行执行，失败时显示 lastError，不与输入轮询抢句柄 |
| 关闭竞争 | Feature Get 过程中关闭 HID | 关闭等待 worker 释放设备句柄，不出现崩溃或悬挂 |

失败定位重点：

- 打开失败时先确认设备未被其他程序占用，再确认 path 或 VID/PID 是否对应同一接口。
- Output 无响应时检查 Report ID、固定报告长度、是否需要首字节长度。
- Feature Get 返回空时检查请求缓冲首字节 Report ID 和 Feature Report 长度。
- 关闭卡住时记录正在执行的操作类型，检查是否有长时间阻塞的 Feature 请求。

## 通过标准

| 类别 | 通过条件 |
|------|----------|
| 自动化测试 | `ComAssistant_tests.exe` 和 `ctest` 全部通过 |
| Raw/OTA | 大文件不一次性占用异常内存，暂停/继续/取消/失败状态可见且准确 |
| X/YMODEM/YMODEM-G | 握手、重发或 G 模式中止、取消、完成路径均能被设备端验证 |
| HID | Input/Output/Feature 均可用，关闭和并发 Feature 操作稳定 |
| 诊断记录 | 每个失败都能在日志中定位到阶段、参数和错误文本 |

完成一轮实机验证后，把日志文件名、设备信息、失败结论和修复 commit 记录到项目维护日志中。
